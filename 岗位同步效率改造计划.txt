下面是针对“游标卡住、同步慢、不同公司相互影响、阶段推进不及时”的全量改进方案。

## 一、目标

| 指标 | 目标 |
|---|---|
| 新岗位进入数据库 | 上游出现后 10 至 15 分钟内 |
| 岗位更新同步 | 15 分钟内 |
| 单条岗位失败 | 不阻塞整页 |
| 单家公司失败 | 不影响其他公司 |
| 游标连续不动 | 2 个周期内报警 |
| 已确认来源公司的字段补全 | 2 小时内完成一轮 |
| 未知来源公司 | 先完成来源探测，不猜字段 |
| 岗位状态安全 | 字段异常绝不自动下架 |

不能承诺“任何情况下零失败”，但可以做到：**失败可定位、可重试、可跳过，不形成全局死锁。**

## 二、总体架构

```text
上游增量 Feed
      ↓
请求层：超时、重试、游标检查
      ↓
页面接收层：验证页面整体结构
      ↓
逐条标准化
  ├─ 单条异常 → 失败队列
  └─ 正常岗位 → 批量写入数据库
                    ↓
          保存成功/失败结果
                    ↓
              推进主游标
                    ↓
              网站 API 查询
```

官方详情补全单独运行：

```text
公司队列
  ├─ Intel
  ├─ Accenture
  ├─ Stripe
  └─ OpenAI
       ↓
各公司独立游标、租约和重试次数
       ↓
只补充有官方证据的字段
```

## 三、第一阶段：先解决游标卡死

这是最高优先级。

当前风险在：

- [job-feed-orchestrator.ts](/D:/UserFiles/Desktop/rising%20path项目/src/lib/job-feed-orchestrator.ts:245)
- [jobs-feed.ts](/D:/UserFiles/Desktop/rising%20path项目/src/lib/jobs-feed.ts:627)

现在 `page.failed > 0` 会让整页游标停住。第一阶段需要把失败拆成两类：

### 可隔离失败

包括：

- 单条经验值异常
- 单条岗位字段超长
- 单条岗位 URL 异常
- 单条岗位写入失败
- 单条字段解析失败

处理方式：

```text
记录失败岗位
继续处理同页其他岗位
保存失败队列
推进主游标
```

### 不可确认失败

包括：

- 上游整页无法读取
- 返回 JSON 结构整体变化
- Supabase 整体不可用
- 数据库连接超时
- 上游游标连续不变化

处理方式：

```text
保留当前游标
当前来源进入 degraded 状态
重试 3 次
触发报警
不影响其他来源和网站读取
```

这样可以避免“第 237 条岗位失败，导致后面几万条岗位都不再同步”。

## 四、第二阶段：建立失败队列

新增 `job_sync_failures` 表，记录：

```text
source_system
company
external_job_id
source_url
operation
payload
error_message
attempts
next_retry_at
status
first_failed_at
last_failed_at
```

重试策略：

```text
第 1 次：1 分钟后
第 2 次：5 分钟后
第 3 次：30 分钟后
第 4 次：2 小时后
第 5 次：进入 dead 队列
```

失败岗位进入 `dead` 后：

- 不再阻塞主同步
- 不再无限重复
- 管理端显示失败原因
- 可以人工重新放回 `pending`
- 每次重试保留原始错误和时间

## 五、第三阶段：提高主同步速度

当前生产每轮处理 10 页，每页 500 条。建议改成自适应模式：

### 正常追赶阶段

- 每页 500 条
- 每轮最多 20 至 50 页
- 数据库每批 100 条
- 读取下一页和写入当前页可以有限流水线执行
- 单次运行最多 5 分钟
- 不超过上游限流阈值

### 已经追平阶段

- 继续使用增量游标
- 只读取上次成功后的变化
- 使用 5 至 10 分钟重叠窗口防止边界遗漏
- 不重复做全量扫描

不能盲目并行请求同一个游标的下一页，因为这样可能造成：

- 页码重复
- 岗位漏掉
- 游标顺序错乱

只有上游支持独立分区或稳定 offset 时，才能并行抓取。

## 六、第四阶段：数据库写入优化

数据库写入必须分成三层：

### 1. 批量写入

正常岗位 50 至 100 条一批写入，减少大量 HTTP 请求。

### 2. 单条降级重试

一批写入失败时：

```text
整批失败
  ↓
拆成单条
  ↓
单条重试
  ↓
仍失败的进入失败队列
```

### 3. 幂等约束

统一使用：

```text
source_system + company + external_job_id
```

没有外部 ID 时使用稳定官方 URL。

不能通过删除重建解决同步问题，否则会破坏：

- 岗位 ID
- 收藏
- 投递记录
- AI 匹配记录
- 字段映射关系

## 七、第五阶段：公司队列公平调度

当前 `nextCompanyIndex` 在进程内存中，服务重启后可能重新从第一家公司开始。应改成数据库持久化调度：

每家公司状态至少保存：

```text
last_attempted_at
last_success_at
next_retry_at
consecutive_failures
cursor
priority
```

每轮选择：

1. 最久未处理的正常公司
2. 有新岗位的公司
3. 用户访问量高的公司
4. 失败但已到重试时间的公司
5. 连续失败的公司最后处理

这样服务重启后不会反复从 Accenture 开始，也不会让某家公司长期得不到处理。

建议：

- 每轮处理 3 至 5 家公司
- 每家公司每批 20 条
- 每个官方域名最多 1 至 2 个并发请求
- 429 使用 `Retry-After`
- 单家公司失败只暂停该公司
- 连续 5 次失败进入人工复核

## 八、第六阶段：公司来源全量管理

针对当前所有活跃公司建立来源矩阵：

```text
公司名
上游 company_id
岗位数量
官方 careers URL
官方 host
来源类型
外部岗位 ID
详情 URL 规则
是否需要详情页
最后成功时间
当前状态
```

来源分为：

```text
Workday
Greenhouse
Ashby
Lever
Phenom
Oracle HCM
Apple API
公司自建 API
待探测
```

处理原则：

- 已确认来源：进入自动字段队列
- 来源不明：只做探测和登记
- 不根据公司名称猜 URL
- 不根据普通页面猜截止日期、薪资或经验
- 不因为详情页失败改变岗位上下架状态

主岗位同步可以覆盖所有公司；官方字段补全只处理已经验证来源的公司。

## 九、第七阶段：每家公司固定完成流程

每家公司都使用相同的阶段门槛：

### 阶段 A：来源探测

- 采集不超过 20 条真实岗位
- 确认官方域名、稳定 ID、列表和详情接口
- 记录字段覆盖情况
- 不写生产字段

### 阶段 B：解析验证

- 添加至少 20 条 fixture
- 验证地点、岗位类型、经验、薪资、截止日期、正文
- 统计解析失败和地区过滤数量

### 阶段 C：生产 dry-run

必须输出：

```text
official_received
official_parsed
matched_external_ids
candidate_jobs
字段候选数量
详情失败数量
关闭数量
```

### 阶段 D：首批写入

- 固定 20 条
- 只补缺失或非 verified 字段
- 不修改岗位状态
- 完成数据库、API、岗位页三处验证

### 阶段 E：全量写入

- 使用公司独立游标
- 分批执行
- 失败进入队列
- 最后 dry-run 候选为 0

### 阶段 F：稳定观察

连续 3 个同步周期满足：

```text
failed = 0 或低于阈值
游标持续推进
岗位数量没有异常下降
官方证据完整
API 和页面一致
```

才标记为常规来源。

## 十、监控和自动处理

必须增加同步监控指标：

```text
feed_cursor_age
cursor_last_progress_at
received
upserted
quarantined
failed
queue_depth
company_queue_age
official_429_count
database_write_latency
lease_age
```

报警条件：

```text
主游标 15 分钟未推进
同一游标连续 2 个周期不变
单页失败率超过 2%
同一公司连续 5 次失败
失败队列超过 1000 条
租约超过 TTL
上游岗位数量突然下降 80%
```

报警后的动作不是全站停止，而是：

```text
岗位字段异常 → 隔离岗位
Intel 官网异常 → 暂停 Intel
Workday 异常 → 暂停 Workday 详情队列
主 Feed 异常 → 暂停主 Feed
网站 API 异常 → 只处理网站，不暂停同步
```

## 十一、实际实施顺序

### 第 1 天

- 增加失败队列表
- 区分 `row_failure` 和 `fatal_page_failure`
- 改造游标提交逻辑
- 增加单条降级重试
- 加入游标无进展报警

### 第 2 至 3 天

- 调整主同步批量写入
- 增加数据库写入耗时监控
- 验证 500、5,000、50,000 条岗位同步
- 观察主游标是否连续推进

### 第 4 至 5 天

- 将官方公司轮转位置持久化
- 增加失败公司的退避和死信状态
- 优化每轮公司数量
- 验证服务重启后不会重复从第一家公司开始

### 第 6 至 10 天

- 完成所有活跃公司的来源矩阵
- 按来源族推进连接器
- 每个来源族先完成一个先锋公司
- 再批量扩展同类公司

### 后续长期运行

- 主岗位增量同步持续运行
- 官方详情按公司独立轮转
- 每周检查失败队列和未知来源
- 每家公司完成 3 个稳定周期后进入常规队列
- 全量对账只在人工维护窗口执行

## 十二、最终效果

改造完成后：

```text
一条岗位失败
→ 进入失败队列，不阻塞页面

一家公司失败
→ 保留该公司游标，不影响其他公司

主 Feed 失败
→ 主 Feed 重试，不影响网站读取旧数据

网站失败
→ 网站暂时显示旧数据，不影响后台同步

服务重启
→ 从数据库持久化状态继续，不从头开始

长期失败
→ 进入 dead 队列，不形成无限循环
```

最关键的改动只有一句话：

> 主游标负责快速接收新数据，失败队列负责修复异常数据，公司队列负责官方字段补全，三者不能再共用同一个阻塞条件。
