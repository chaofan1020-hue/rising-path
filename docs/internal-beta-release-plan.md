# Liorvix 内测优先发布计划

## 决策与目标

下一阶段不再以“完成全部功能”为上线条件，而是先交付一个受邀请、可计量、可暂停的内测版本。目标是在不失控消耗 AI 与语音成本的前提下，验证留学生是否能完成一条有价值的求职准备路径：

```text
受邀注册 -> 上传并确认简历 -> 找到岗位 -> AI 匹配/优化 -> 模拟面试 -> 记录投递 -> 提交反馈
```

内测默认只面对小规模白名单用户。公开注册、真实支付和大规模自动网申不属于本轮发布范围。

## 当前基础与缺口

| 能力 | 当前基础 | 内测前需要补齐 |
| --- | --- | --- |
| 身份与隔离 | 邮箱、OTP、Google OAuth、Bearer token、RLS 已有 | 邀请/白名单拦截和测试账号管理 |
| 核心求职路径 | 简历、岗位、匹配、优化、面试、投递等主链路已有 | 用真实凭据完成整链路验收，明确内测保留功能 |
| 成本可见性 | `ai_usage_events`、模型价格快照、学生用量汇总、后台导出已有 | 额度判定、预警、冻结和用户可见剩余额度 |
| 运营能力 | 管理员角色、审计、学生目录、服务健康看板已有 | 内测用户开关、额度调整、异常处理 SOP |
| 商业化 | 已有可追溯的 AI 成本数据 | 套餐、权益、订单、支付回调和账务状态契约 |

关键结论：现有“记录用量”不能替代“拦截用量”。内测前必须在所有会触发付费 AI/语音调用的服务端入口执行统一额度检查，客户端按钮禁用只能作为体验提示，不能作为成本控制手段。

## 内测范围

### 必须交付

- 受邀请注册和登录；管理员可启用、暂停、到期或移除内测资格。
- 每名内测用户仅可保留有限数量的简历，完成简历上传、解析、画像确认。
- 岗位浏览、收藏、岗位匹配、简历优化、模拟面试、投递记录和反馈闭环。
- AI 文本、ASR、TTS 调用均在服务端执行额度检查、记账和失败记录。
- 实时语音 WebSocket 在内测默认关闭，直到连接级实际时长可以结算；用户使用受控的文字或 HTTP 语音回退。
- 管理员可查看单用户与全体内测的调用次数、Token/音频时长、预计成本、额度余量和异常原因。
- 关键错误告警、数据库备份/恢复说明、回滚步骤、移动端与桌面端主链路验收。

### 内测期间收敛

- 自动网申仅保留“用户确认后辅助填表/记录”能力；不承诺无人值守自动提交。
- 企业 DNA 扩展、复杂推荐策略、视觉重构、增长活动和大规模岗位采集不阻塞内测。
- 只开放已通过浏览器和真实服务验收的地区、语言和语音模式；未验证组合默认关闭。
- 不接入真实扣款，不展示可购买商品，也不允许通过前端参数提升额度。

## 内测额度与风控设计

### 权益模型

建立独立于具体支付渠道的权益层。每个用户在一个结算周期内只有一个有效权益快照，内部测试默认使用 `beta` 套餐；管理员可为个别用户增加临时额度或设置永久白名单，但所有调整必须写入审计日志。

建议内测初始额度按“完成一次完整体验”设置，并在首批真实成本数据后再调整：

| 能力 | beta 默认额度 | 计量单位 | 超额行为 |
| --- | ---: | --- | --- |
| 简历解析 | 3 | 次 / 周期 | 拒绝新解析，保留已有简历 |
| AI 选岗/评分 | 10 | 次 / 周期 | 返回剩余量和下次恢复时间 |
| 简历优化 | 5 | 次 / 周期 | 拒绝生成；已保存版本仍可编辑/导出 |
| 模拟面试 | 3 | 场 / 周期 | 不创建新会话 |
| 语音输入 | 30 | 分钟 / 周期 | 自动降级为文字输入 |
| 语音播报 | 30 | 分钟 / 周期 | 自动降级为文字回复 |

周期建议使用固定的自然月 UTC 区间，并允许在内测首月按邀请日开始的 30 天做一次性迁移。所有计数仅在成功领取调用资格后扣减；供应商调用失败或请求取消必须释放或冲正预留额度，避免用户为系统故障付费。

### 强制执行点

1. 在每个 AI/语音 API 入口认证成功后、调用供应商前执行原子“检查并预留”操作。
2. 成功时确认消耗，并把权益快照、计量类型、预留记录 ID 写入用量事件元数据。
3. 失败、超时或取消时释放预留；所有状态迁移必须幂等，避免浏览器重试重复扣额。
4. 未授权、无内测资格、账户暂停、额度不足和系统熔断分别返回明确的机器码与用户提示。
5. 为用户设置单请求、单日和全局安全阈值；全局阈值到达时停止新的高成本能力，只保留查看和编辑已有数据。

### 建议数据契约

| 表/对象 | 关键字段 | 用途 |
| --- | --- | --- |
| `access_entitlements` | `user_id`, `plan_code`, `status`, `period_start`, `period_end`, `source`, `version` | 用户当前可用权益快照 |
| `entitlement_limits` | `plan_code`, `metric`, `limit_value`, `overage_policy`, `active_from` | 套餐/内测额度版本，避免在代码中硬编码 |
| `usage_reservations` | `user_id`, `metric`, `amount`, `status`, `idempotency_key`, `expires_at` | 调用前的原子预留、确认、释放与过期回收 |
| `billing_customers` | `user_id`, `provider`, `provider_customer_id` | 支付渠道客户映射，内测可为空 |
| `billing_orders` | `user_id`, `plan_code`, `amount`, `currency`, `status`, `provider_order_id` | 订单事实，不从回调直接改权益 |
| `billing_webhook_events` | `provider`, `event_id`, `payload`, `processed_at`, `result` | 回调去重、审计和可重放 |

所有表启用 RLS。客户端仅可读取自己的当前权益与脱敏用量摘要；套餐配置、订单、回调和额度调整只由服务端及具备专门权限的管理员处理。

## 支付预留边界

本轮只搭建商业化边界，不接真实渠道：

- 定义 `BillingProvider` 适配接口：创建结账会话、查询订单、验证回调、取消订阅/退款、客户门户。
- 实现内部 `manual_beta` 提供方，用管理员授权直接创建 `beta` 权益，走与未来支付成功相同的“订单 -> 权益”状态机。
- 支付 API 只返回未启用状态或受控的套餐目录；生产支付密钥、回调地址、税务与退款策略未确认前，不暴露支付按钮。
- 任何支付成功均通过经过签名验证、可幂等重放的 webhook 事件落单，再由服务端授予/续期权益；绝不以前端“支付成功”回调授予额度。
- 选择渠道时再按运营主体和目标市场决定国内支付、国际支付或双渠道。接口和表结构不依赖某一家提供商。

## 重排后的执行顺序

### 阶段 A：内测基线与范围冻结（3-5 天）

- 确定首批人数、目标市场、内测周期和每用户成本上限；建议从 20-30 名活跃用户开始。
- 列出允许进入内测的功能开关、降级路径和明确不开放的能力。
- 在 staging 按迁移顺序核对数据库、RLS、存储权限、OAuth/邮件回调、AI/ASR/TTS 凭据与模型价格。
- 使用真实账号走通注册、简历、岗位、优化、面试、投递和反馈；阻断任一无法恢复的主链路故障。

验收：可邀请的 staging 环境可重复部署；核心链路有成功、失败、未登录和重复提交测试；内测手册与回滚路径可执行。

### 阶段 B：资格、额度与运营控制（5-7 天）

- 落地上述权益、限额和预留数据模型及 RLS。
- 为简历解析、匹配/评分、优化、面试、ASR、TTS 接入统一服务端额度中间层。
- 增加账户状态和功能开关：仅邀请、启用、暂停、到期、全局熔断、语音降级。
- 后台补齐内测用户列表、单用户额度编辑、用量/成本/失败明细、阈值预警和审计。
- 提供用户侧用量摘要与额度耗尽提示，不暴露内部单价和供应商细节。

验收：并发请求、重试、供应商失败、过期预留、管理员暂停和全局熔断均不会多扣或漏扣；无资格用户无法触发付费调用。

### 阶段 C：支付就绪但未启用（3-5 天）

- 落地套餐、订单、支付事件和权益授予状态机；`manual_beta` 全链路可用。
- 定义支付提供方适配接口、接口权限、回调验签和幂等测试，不配置真实支付凭据。
- 配置未来可售套餐的权益版本、展示文案占位和价格字段，但在用户界面保持关闭。
- 建立订单、退款/撤销和权益变更审计，不在本阶段处理真实资金。

验收：管理员授予的 beta 权益与未来支付成功后的权益走同一状态机；重复事件不会产生重复额度；支付模块关闭时不影响内测主流程。

### 阶段 D：小规模内测运行（2 周，持续迭代）

- 分批邀请：先 5 名内部验证用户，再 20-30 名目标用户；每批稳定 48 小时后再扩大。
- 每日查看成本、额度命中率、失败率、解析成功率、完成漏斗和高频反馈；优先修复阻塞链路与成本异常。
- 每周复盘实际单用户成本与配额，修改“套餐额度版本”而不是散落在代码中的常量。
- 只在核心路径稳定后开放更多地区/语音模式或增加人数。

验收：连续 7 天无 P0/P1 数据隔离或重复计费问题；关键 AI 调用可追踪；单活跃用户成本在预设上限内；至少形成一轮可行动的用户反馈清单。

### 阶段 E：公开上线准备（内测指标达标后）

- 根据真实成本和留存确定正式套餐、免费试用策略、支付渠道、币种、税务和退款政策。
- 接入已选支付提供方，实现受控灰度结账、签名回调、账单支持与客服流程。
- 完成隐私政策、服务条款、数据删除/导出、监控告警、备份恢复演练、容量与安全评审。
- 先对少量新注册用户灰度支付，再逐步开放注册与商业化入口。

## 内测仪表盘与停止条件

每天至少看以下指标：

- 活跃内测人数、邀请转化、简历确认率、匹配/优化/面试完成率、投递记录率、反馈提交率。
- 每用户和全局的调用量、Token、音频分钟数、预计成本、额度命中率、预留超时率和供应商错误率。
- 解析失败率、AI 响应超时率、登录/上传失败率、岗位链接健康度以及数据隔离异常。

立即暂停新增邀请或相关高成本能力的条件：

- 任意跨用户数据可见、鉴权/RLS 绕过、重复授予权益或重复扣额。
- 日成本达到预算的 80%，且无法由已有额度或供应商异常解释。
- 关键 AI 服务连续异常，或核心路径成功率显著低于预设阈值。

## 首个开发周期清单

1. 冻结内测范围并给每项 AI/语音能力定义计量单位、默认额度和降级行为。
2. 新建权益、额度、预留、订单和支付事件迁移，补齐 RLS 与服务端 RPC。
3. 实现统一额度服务并先接入简历解析、AI 匹配、简历优化和面试创建；再接 ASR/TTS。
4. 扩展管理员学生详情为“内测资格与额度”工作台，所有调整写审计日志。
5. 增加 `manual_beta` 权益授予流程、支付适配接口和状态机测试。
6. 在 staging 完成浏览器回归和并发/幂等测试后，再开始第一批 5 名用户内测。
