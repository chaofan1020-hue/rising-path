# AI 模拟面试公司与岗位选择异常情况说明

**日期：** 2026-08-13
**范围：** 模拟面试设置页的公司选择、岗位选择和企业面试基因预览
**结论：** 该问题已完成代码修复：公司列表改为数据库端去重；设置页和面试开场都只读取已有 DNA，不再为未知公司触发 LLM；公司、岗位和 DNA 请求均已支持取消与过期响应丢弃。手动公司仍是允许的业务路径，但会与岗位库公司明确区分。

## 一、用户可见现象

1. 打开模拟面试设置页或切换公司时等待时间较长，岗位列表和企业 DNA 预览不是同时完成。
2. 公司下拉框只显示少量公司，无法覆盖岗位库中实际存在的公司。
3. 选择公司后，岗位下拉框可能为空或数量很少；用户容易判断为“数据库没有岗位”。
4. 在未选择岗位、直接填写目标公司时，可以生成一个岗位库或企业 DNA 精调库中没有的公司基因。
5. 快速切换公司时，旧的 DNA 请求可能晚于新请求返回，造成预览内容与当前选择的公司不一致。

## 二、当前实际调用链

### 1. 公司与岗位

前端文件 `src/app/mock-interview/page.tsx` 的行为如下：

- 页面加载调用 `GET /api/interview/jobs` 获取公司列表。
- 选择公司后调用 `GET /api/interview/jobs?company=...` 获取岗位。
- 岗位接口查询 `jobs` 表，并限制 `is_active=true`，再按 `region` 过滤目标地区。
- 选择岗位后，启动请求使用岗位的公司；未选择岗位时，启动请求直接使用用户填写的 `targetCompanyInput`。

### 2. 企业 DNA

前端在公司名变化后等待 600ms，再调用 `GET /api/company-dna?name=...`。服务端 `src/lib/company-dna-service.ts` 的查找顺序是：

1. `company_dna` 中人工编辑版本；
2. 代码内精调 DNA；
3. `company_dna` 中的缓存；
4. 对任意公司名调用 LLM 生成，并尝试写回 `company_dna`。

该接口没有要求公司必须先存在于 `jobs.company`，所以 DNA 数据源不是岗位主数据的强约束子集。

## 三、已完成的数据库与接口核查

使用当前 `.env.local` 配置的 Supabase 服务端连接进行只读统计，结果如下：

| 检查项 | 结果 |
| --- | ---: |
| `jobs` 总记录数 | 32,271 |
| `jobs` 中 `is_active=true` 且符合目标地区的记录数 | 24,776（Supabase `count=exact` 与完整分页结果一致） |
| 目标地区有效岗位对应的去重公司数 | 73 |
| `company_dna` 记录数 | 2 |
| 当前 `company_dna` 公司 | `meta`、`Accenture` |
| `company_dna` 中不在目标地区岗位公司集合的记录 | `meta` 1 条 |

### 公司列表截断的直接证据

对同一套地区条件直接分批查询 `jobs` 表，得到 73 家公司，包括 JPMorgan Chase、Goldman Sachs、Google、Microsoft、Meta、OpenAI、Stripe 等。

但访问当前服务端接口：

```text
GET /api/interview/jobs
200
{"companies":["Accenture","Adobe","Amazon"]}
```

代码中的公司聚合查询没有 `.range()` 分页，也没有显式提高返回上限：

```ts
client
  .from('jobs')
  .select('company')
  .eq('is_active', true)
  .or(targetRegionPostgrestClauses().join(','))
  .order('company');
```

Supabase/PostgREST 默认最多返回 1,000 行。由于结果按 `company` 排序，前 1,000 行被前几个公司占据，应用层去重后只得到 `Accenture`、`Adobe`、`Amazon`。因此这是接口分页缺失造成的确定性截断，不是岗位数据真的只有 3 家公司。

### 岗位接口的表现

```text
GET /api/interview/jobs?company=JPMorgan%20Chase
200
耗时约 916 ms，返回 50 条岗位（接口自身 limit=50）
```

这说明岗位表中确实存在 JPMorgan Chase 的有效岗位；它未出现在公司下拉框，是公司聚合接口被 1,000 行上限截断导致的连锁问题。

### 接口耗时观察

在本地自定义 server `http://127.0.0.1:5055` 上测试：

| 请求 | 观察耗时 | 说明 |
| --- | ---: | --- |
| `/api/interview/jobs` | 约 4.0 秒 | 查询未分页，返回前需扫描/传输较多行；服务端和数据库耗时需继续拆分监控 |
| `/api/interview/jobs?company=JPMorgan%20Chase` | 约 0.9 秒 | 返回最多 50 条岗位 |
| `/api/company-dna?name=...` | 未在未登录脚本中直接压测 | 需要登录态；未知公司会进入 LLM 生成路径，耗时可能达到数秒至几十秒 |

## 四、根因分析与修复状态

### P0：公司聚合接口缺少分页（已修复）

这是“公司列表不全”的首要根因。旧接口默认只拿到前 1,000 行，再在应用层去重，不能代表全量公司。当前接口已按页读取目标地区有效岗位并在服务端去重，返回完整公司集合。

### P1：岗位接口存在额外地区过滤（当前产品口径）

岗位查询强制使用目标地区 `region.ilike` 条件。数据库中存在但地区不匹配、地区字段为空或使用未覆盖城市写法的岗位不会显示。这是第二类“数据库有，但列表看不到”的原因，必须在界面上明确提示当前筛选口径。

### P1：企业 DNA 和岗位公司不是同一张主数据表

`jobs.company` 是岗位来源；`company_dna.company_name/aliases` 是人工、精调和历史生成内容的混合缓存。两者天然可能不一致。`company_dna` 只有 2 条记录，不能被当作完整公司目录。

### P1：手动目标公司允许任意字符串

未选岗位时，前端允许输入任意 `targetCompanyInput` 并直接启动面试。该值不经过 `jobs.company` 校验，也不要求存在于 `company_dna`，因此服务端会为新公司生成 DNA。这是当前设计允许的行为，不是数据库查询异常。

### P1：DNA 预览可能同步触发 LLM（已修复）

旧实现中，公司名变化后的预览请求会在无精调、无缓存时调用外部 LLM 并写库。当前预览和面试开场只返回已有的人工、精调或缓存 DNA；未知公司显示暂无预览并直接按岗位 JD 开始，不在用户等待路径生成。

### P1：前端请求没有取消和竞态保护（已修复）

岗位和 DNA 请求现在都使用 `AbortController`，并以当前公司/当前请求作为状态更新条件。快速切换时，旧请求会取消或被丢弃，不得覆盖最后一次选择。

### P2：DNA 全表读取后应用层模糊匹配（后续优化）

`company-dna-service.ts` 当前读取 `company_dna` 全表，再对公司名和别名进行规范化及包含匹配。表量较小时影响有限，但随着生成缓存增长，查询延迟和误命中风险都会增加。

## 五、影响范围与风险

- **功能正确性：** 公司下拉列表不完整，用户无法稳定选择真实岗位公司。
- **数据一致性：** DNA 可能属于用户手动输入的公司，而岗位、JD 和公司选择并不对应。
- **用户体验：** 公司切换同时触发岗位查询和 DNA 查询，未知公司还会触发 LLM，造成卡顿。
- **成本：** 每次预览未知公司都可能消耗一次文本模型调用，并写入共享 DNA 缓存。
- **结果可信度：** LLM 对公开信息不足的公司会按行业头部公司风格推断，不能等同于企业真实面试基因。
- **并发稳定性：** 快速切换、重复点击或网络重试可能造成旧响应覆盖新状态。

## 六、已实施修复与后续项

### P0：公司列表正确性（已实施）

1. 公司聚合接口已使用分页读取全部目标地区有效岗位后去重，不再依赖默认 1,000 行响应上限。
2. 为 `jobs` 增加规范化公司名字段和索引，避免每次传输大量重复公司名。
3. 接口返回 `total`、`appliedRegionFilter` 和 `hasMore`，前端能明确显示筛选口径。
4. 增加回归测试：数据库有 73 家公司时，接口不能只返回前 3 家。

### P0：隔离数据库公司与自定义公司（已实施）

1. 公司选择器只展示 `jobs.company` 中的公司。
2. 手动输入单独标注为“自定义公司”，不能伪装成岗位库公司。
3. 启动面试时记录 `companySource=job_catalog|custom_input`，报告中展示来源。
4. 如果选择了岗位，服务端以岗位记录中的公司为准，不信任客户端单独传入的公司名。

### P1：消除选择页卡顿（已实施，计时指标待补）

1. DNA 预览和面试开场只读取精调/缓存，不触发 LLM；未知公司显示“暂无企业基因”，并按岗位 JD 直接开始面试。
2. 岗位和 DNA 请求已增加 `AbortController` 及当前选择校验，旧请求取消或丢弃。
3. 公司目录增加 60 秒进程内短 TTL 缓存；岗位明细仍按当前公司取消旧请求。
4. 岗位请求与 DNA 预览已拆开处理；`requestId`、TTFB 和总耗时埋点仍待接入统一观测表。

### P1：提高 DNA 可信度和成本可控性

1. 对 DNA 生成增加显式确认、限流和单场额度。
2. 生成内容标记 `source=generated`，不得与人工/精调 DNA 使用同一可信度文案。
3. 使用数据库规范化名称、别名索引或 RPC，替代全表应用层模糊匹配。

## 七、验收标准

- 公司接口返回目标地区岗位对应的完整去重公司集合，不受 1,000 行默认上限影响。
- 选择任一返回公司后，岗位接口能返回该公司的有效岗位；无匹配时明确显示地区过滤原因。
- 选择公司时 DNA 预览 P95 不触发外部 LLM，页面不会因 DNA 生成阻塞岗位选择。
- 快速切换公司 10 次，最终预览和岗位列表必须与最后一次选择一致。
- 自定义公司与岗位库公司在 UI、请求和报告中有明确来源标识。
- 同一未知公司重复预览不会重复生成或重复扣费。

## 八、补充说明：部署与迁移

此前升级方案中的 `0025_interview_core_upgrade.sql` 已在当前远端 Supabase 环境执行，不能重复执行同一迁移。实时 ASR/TTS 仍需使用项目自定义 server 启动（`pnpm dev` 或构建后的 `pnpm start`），但这与本次公司/岗位列表截断问题是两个独立问题。

当前模拟面试产品边界为纯语音全真模拟：麦克风是必备设备，拒绝权限、无设备或设备被占用时应明确阻断并提供重试/诊断，不提供文本回答替代；视频仅保留浏览器本地预览，不上传也不参与视觉评估。
