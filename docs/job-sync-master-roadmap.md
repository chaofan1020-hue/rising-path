# 岗位同步长期治理总计划

更新时间：2026-09-03

## 1. 目标与边界

这份计划是岗位同步问题的长期总入口，适用于上游官网采集、上游到美国服务器、美国服务器到 Supabase、官网字段补全、岗位生命周期、监控大屏和以后新增公司。

最终目标：

- 官网有的岗位能够稳定进入上游和网站。
- 官网已经撤下的岗位不会长期留在网站在招列表中。
- 上游列表不完整、接口异常、验证码、超时或数量未知时，不批量关闭岗位。
- 每一家公司都能看到当前处理阶段、已处理岗位、剩余岗位、失败原因和下一步动作。
- 一家公司出问题时只隔离这一家公司，不拖停其他公司和主 Feed。
- 所有岗位状态变化都有来源证据、时间和可恢复记录。

不改变的边界：主 Feed 的游标顺序、现有分页协议、并发上限和公司轮换逻辑，除非单独评审并获得明确授权。字段补全不能修改岗位 ID、收藏、投递、AI 匹配或岗位上下架状态。

## 3. 阶段一：上游采集正确性与严格快照

### 3.1 统一上游目录契约

`GET /dashboard/company-directory` 必须继续返回数组顶层结构，并为每家公司提供：

`id`、`name`、`open_jobs`、`official_open_jobs`、`official_count_status`、`official_count_source`、`official_count_observed_at`、`last_crawl_at`、`latest_run_status`、`generated_at`、`contract_version`。

规则：

- 未知数量使用 `null`，不能使用 0、9999 或 99999。
- 失败运行不能覆盖上一次可信的官方数量。
- `partial` 只有在官方列表完整但字段质量有少量问题时，才可以继续使用官方数量对账。
- `capped_unavailable` 只能显示下限，不能当成精确数量。
- 数量、状态和时间必须来自同一个生产快照，不能混用不同运行记录。
- 保留旧客户端字段，避免上游接口升级导致美国端解析失败。

### 3.2 每个连接器的完整性判定

每个来源族必须分别定义：

- 官方报告总数如何取得。
- 唯一外部 ID 如何确定。
- 重复展示如何统计。
- 无效行如何统计。
- 分页、分区和重试如何停止。
- 什么时候允许标记完整。
- 什么时候必须保留游标并禁止关闭岗位。

硬规则：

- `唯一岗位数 + 同一快照内重复展示数` 覆盖官方报告总数，且分页边界完成，才可标记完整。
- 重试轮次之间不得累计重复数、无效数或接收数。
- 页面级失败保留游标；行级失败进入失败队列并允许主游标推进。
- 完整性未确认时，不能批量关闭本地岗位。
- 详情接口 404/410 与 403/429/超时必须分开处理；后者不能当作岗位撤下。

### 3.3 当前重点公司

1. JPMorgan：观察新规则连续三个同步周期，确认撤下岗位只按完整快照处理。
2. Amazon：拆分供应商 10,000 条上限、分区计数和真实官方总数，未取得精确总数前保持未知或下限。
3. Accenture：核查 Workday 分区、无效行和重复 ID，不能用 21,790 与 20,873 的差异直接关闭岗位。
4. Bank of America：确认 14,384 是真实官方总数还是错误聚合，先修复分区/地区口径。
5. Microsoft：核查官方报告 2,178 与抓取 2,131 的 47 条差异，确认是否为列表动态变化、地区过滤或遗漏。

每家公司完成后必须保存：原始计数证据、唯一 ID 清单摘要、重复分布、缺失分布、运行 ID、修复前后数量和回滚点。

## 4. 阶段二：美国端主 Feed 稳定性

主 Feed 只负责把上游变化可靠接收进网站，不负责猜测官网字段，也不依赖字段复核结果。

待完成事项：

- 持续验证每页成功后保存游标，页面级失败不推进游标。
- 验证行级失败不会阻塞同页其他岗位，失败记录进入 `job_sync_failures`。
- 验证批量写入失败会降级逐条重试，最终失败进入死信队列。
- 验证服务重启、多实例和租约过期后从持久化状态继续，不从第一家公司重跑。
- 验证主 Feed、官方字段队列和失败队列使用不同租约，互不阻塞。
- 验证主 Feed 不因为详情页失败、字段缺失或官网数量未知而关闭岗位。

验收指标：

- 新岗位通常在 10 至 15 分钟内进入网站。
- 主游标超过 15 分钟无进展时产生告警。
- 页面级失败保留游标；行级失败率超过阈值时只降级当前页或当前公司。
- 同一公司连续五次失败后进入人工处理，但不暂停全站。

## 5. 阶段三：75 家公司来源矩阵收口

按来源族推进，不按公司名称猜测接口：

1. Oracle HCM：完成 JPMorgan 后复核其他 Oracle 公司。
2. Workday：逐一核对 tenant、站点标识、地区分区和分页边界。
3. Greenhouse、Ashby、Lever、Phenom：复用已验收连接器，确认 board token 和详情 URL。
4. Apple API、公司自建 API：保存请求契约、字段证据和版本变化记录。
5. Amazon、Avature、Eightfold、Taleo、iCIMS 等：先完成来源探测，再决定是否新增连接器。
6. 仍无法确认来源的公司：保持 `discovery_required`，主 Feed 可以继续同步，但官方字段不猜测、不写入。

每家公司必须登记：官方 careers URL、官方 host、来源族、上游 company ID、外部 ID 字段、详情 URL 规则、地区范围、字段覆盖率、快照数量、最后成功时间和状态。

每完成 5 家公司生成一次报告，报告至少包含：官方岗位数、上游岗位数、唯一 ID 匹配数、上游独有数、本地独有数、重复数、快照新鲜度、字段覆盖率和失败原因。

## 6. 阶段四：官方字段补全与历史复核

六项字段固定为：地点、工作方式、岗位类型、经验、薪资、截止日期。

处理顺序：

1. 已确认官方来源的公司进入独立 `official:*` 队列。
2. 每家公司使用独立游标、租约、批次和退避，不等待主 Feed。
3. 正常公司按批次连续处理；只有页面级失败、连接器异常或租约失效才跳过当前公司。
4. 写入只补缺失字段或没有官方证据的旧字段。
5. `unavailable_on_official_source` 显示“官网未提供”，不计为解析失败。
6. 字段解析失败进入失败队列，不修改 `is_active`、`is_closed`。
7. 每家公司完成 canary、全量回填和三周期观察后，才标记为常规来源。

历史复核必须显示真实结果：本轮候选、已处理、已更新、跳过、失败、剩余、最近岗位 ID、最近心跳、主要缺失字段和失败队列数量。不能只显示一个“待复核”总数。

## 7. 阶段五：严格官网下架与历史岗位对账

岗位关闭只能来源于以下证据：

- 上游明确返回关闭事件。
- 官方完整列表快照中缺失，并且连续多个周期确认缺失。
- 官方详情明确返回 404/410 或关闭状态，并排除临时访问错误。

不得依据以下情况关闭：

- 官网数量未知或快照过期。
- 列表分页中途失败。
- 403、429、超时、DNS、验证码或代理错误。
- 详情接口暂时没有正文。
- 字段缺失、字段解析失败或岗位描述过短。

对账输出必须按公司提供：官方唯一 ID、上游唯一 ID、本地在招唯一 ID、三方交集、官方独有、上游独有、本地独有、重复 ID、连续缺失次数和处理建议。

任何批量关闭前必须：

- 生成可恢复清单。
- 记录运行 ID 和官方证据时间。
- 检查收藏、投递和 AI 匹配关联。
- 只更新岗位状态，不删除岗位记录。
- 关闭后验证数据库、公共 API 和岗位详情页。

## 8. 阶段六：同步大屏与人工干预

大屏必须用易懂的三段式语言展示：

`官网岗位 → 上游采集 → 网站数据库`。

每家公司的卡片必须明确标注公司名，并显示：

- 当前阶段：抓官网、传到上游、写入数据库、字段补全、等待重试或已完成。
- 本轮目标岗位数、已处理、剩余、成功写入、关闭、跳过、失败。
- 当前正在处理的公司和并发槽位，明确标注第 1/3、2/3、3/3。
- 最近心跳、最近成功、最近失败、下次重试和运行耗时。
- 当前阻塞原因的自然语言说明，例如“官网分页少返回 47 条，暂不关闭岗位”。
- 官方数量状态：准确、下限、未知、快照过期，不能显示成 0。

人工操作只允许通过后台 API，并且必须二次确认、写入审计日志：

- 重试某家公司。
- 暂停某家公司官方字段队列。
- 释放过期租约。
- 将死信记录恢复为待重试。
- 重新运行指定公司的只读对账。
- 查看并下载脱敏对账报告。

默认禁止直接在大屏执行：改游标、批量关闭岗位、删除岗位、清空失败队列、重建岗位。

所有按钮必须返回明确结果：操作 ID、影响公司、影响记录数、是否真正写入、下一步状态和错误原因。

## 9. 阶段七：监控、告警和故障处理

持续记录：

- 主 Feed 游标年龄和最后进展时间。
- 每家公司当前阶段、批次、已处理和剩余。
- 官方队列年龄、租约年龄和退避时间。
- 官方快照新鲜度、数量状态和数量变化幅度。
- received、upserted、closed、skipped、row failures、fatal failures。
- 数据库批量写入耗时、单条降级次数和失败队列深度。

告警条件：

- 主 Feed 15 分钟无进展。
- 同一游标连续两个周期不变。
- 公司连续五次失败。
- 失败队列超过 1,000 条。
- 官方数量突然下降 80% 以上。
- 租约超过 TTL 未释放。
- 快照过期或官方数量从准确变为未知。

故障动作：

- 岗位行异常：隔离行，继续主游标。
- 一家公司异常：暂停该公司，其他公司继续。
- 单一 ATS 异常：暂停该来源族字段队列。
- 主 Feed 异常：保留游标并告警，网站继续提供上一次有效数据。
- 数据库异常：停止写入并保留游标，不执行补偿性删除。

## 10. 阶段八：以后新增公司固定流程

以后新增公司必须严格遵循 [`job-company-onboarding-runbook.md`](job-company-onboarding-runbook.md)：

1. 检查上游、美国台账和官网是否已存在，防止重复公司。
2. 登记官方 careers URL、来源族、地区范围、上游 company ID 和外部 ID。
3. 先探测官方列表和详情，不使用搜索结果或模型猜测。
4. 抓取不超过 20 条真实岗位做 dry-run，不写生产字段。
5. 若是新来源族，先新增连接器、字段规则、脱敏 fixture 和回归测试。
6. 生产执行 20 条 canary，只补官方证据字段，不改变岗位生命周期。
7. 验证生产数据库、公共 API、岗位详情页和大屏四处结果。
8. 再进行全量字段补全，使用独立游标和失败队列。
9. 连续三个同步周期稳定后，才标记为常规来源。
10. 如果公司暂时没有岗位，也必须保留台账卡片，数量显示未知或 0 条真实岗位，不能伪造上游数量。

新增公司完成标准：上游目录和美国台账 ID 一致；来源证据可追溯；外部 ID 无重复；官方数量口径明确；失败可重试；岗位页面和 API 一致；没有因为接入修改其他公司的岗位状态。

## 11. 阶段九：生产发布、回滚和数据保护

每次发布顺序：

1. 本地类型检查、Lint、连接器测试和针对性脚本测试。
2. 备份远程代码、配置和当前运行摘要。
3. 先部署数据库迁移，再部署上游接口，再部署美国应用。
4. 先做只读 dry-run，再做 20 条 canary。
5. 观察至少三个同步周期。
6. 最后才扩大到全量任务。

回滚原则：

- 优先回滚单个连接器或单家公司配置。
- 不回滚整个数据库，不删除岗位历史。
- 不把本地 `.env.local` 当生产环境。
- 不在代码、日志、fixture 或文档中写密码、Cookie、API Key 或原始 payload。
- 任何批量状态变更都保留可恢复清单和审计日志。

## 13. 总验收标准

只有同时满足以下条件，才认为岗位同步治理完成：

- 所有活跃公司都有来源台账和明确状态。
- 官网、上游、数据库和网站展示的数量口径带时间戳且可追溯。
- 任意异常公司可以在大屏看到具体阶段、岗位进度、剩余数量和阻塞原因。
- 任意页面级失败不会推进错误游标，也不会关闭岗位。
- 任意行级失败不会阻塞整页或其他公司。
- 官网已确认撤下的岗位能够安全关闭，且不会删除用户关联数据。
- 字段补全只写官方证据，官网未提供字段明确显示“官网未提供”。
- 新公司可以按照固定手册接入，不依赖临时记忆或临时脚本。
- 连续三个同步周期无未解释的数量跳变、游标停滞或跨公司阻塞。

## 16. 快速推进方案

### P0：先恢复可证明的岗位同步主线

目标：保证岗位新增、更新、关闭都按时进入网站，并且任何一次失败都能定位。

执行顺序：

1. 确认生产唯一主 Feed 入口：是 systemd、应用内 worker 还是其他调度器；停用重复触发入口。
2. 修复并启用主 Feed 定时任务，至少每 5 至 10 分钟触发一次增量同步。
3. 运行一次只读健康检查，验证上游 HTTP 200、契约版本、游标存在、第一页岗位结构正确。
4. 运行一轮小预算增量同步，确认页面成功后游标前进、行级失败进入失败队列、页面级失败保留游标。
5. 连续观察三个周期：新增、更新、关闭数量都要有运行记录；没有变化也必须记录“本轮无变化”，不能显示空白。
6. 将主 Feed 的成功时间、最后心跳、当前阶段和失败原因接入大屏；若超过 15 分钟无进展，状态必须变成“主同步停滞”。

完成门槛：主 Feed 连续三个周期成功或可解释 partial；没有未解释的旧 `running`；站点岗位 API 和数据库状态一致。

### P1：清理假运行和暂停队列状态

目标：大屏显示的“正在处理”和“已暂停”必须与实际 worker 状态一致。

执行顺序：

1. 只处理心跳过期且没有有效租约的 `job_sync_runs`，标记为 `aborted/stale`，保留原始指标。
2. 释放已经过期的公司租约，不清空有效游标，不重置已完成公司的游标。
3. 对历史复核队列统一执行状态对账：来源台账、复核表、同步状态表三者必须一致。
4. 把 51 家 `completed` 公司从候选调度中排除，只保留新增岗位或新字段缺口的增量任务。
5. 对 24 家暂停公司分别写明“待探测”“等待开关”“官方接口异常”“混合来源待拆分”等下一步，不允许统一显示为暂停。
6. 大屏增加“实际 worker 心跳”和“租约有效期”两项，旧运行记录不能占用并发槽位。

完成门槛：没有过期运行记录被显示为正在处理；每个暂停公司都有明确恢复条件；队列调度可以自动跳过暂停公司并继续其他公司。

### P2：优先处理对 AI 选岗影响最大的字段和公司

目标：优先提高 AI 实际使用的岗位字段质量，不追求没有证据的字段填满。

优先级：

1. 高岗位量且来源已确认：Google、Microsoft、Apple、Accenture、NVIDIA、Intel。
2. 高用户价值且来源待探测：JPMorgan Chase、Deloitte、Morgan Stanley、Goldman Sachs、UBS。
3. 已完成公司：只处理新岗位和新增字段缺口，不重新全量扫描。
4. Amazon：先解决官方详情 404/关闭状态和供应商数量上限，再决定是否打开写入开关。

每家公司必须按“20 条真实样本 dry-run → 20 条 canary → 全量分批 → 三周期观察”推进。字段只接受官方证据；官网未提供单独记录为 `unavailable_on_official_source`。

### P3：逐步收口 24 家暂停公司

按岗位量和可执行性推进，不按公司名称跳跃：

1. 先完成 JPMorgan、Lazard、Jefferies 的 Oracle HCM 状态收口和台账一致性检查。
2. 再处理 Deloitte、Morgan Stanley、Goldman Sachs、UBS 等高岗位量来源探测。
3. 然后处理 Bain、BlackRock、Citadel、Duolingo、Elastic、Evercore、KKR、McKinsey、MongoDB、Okta、Roblox、Rothschild、Two Sigma、Millennium 等较小批次。
4. 每次最多推进 1 家高风险公司或 2 家低风险公司；一个来源族的先锋未通过时，不批量打开同族写入。

### P4：建立自动化闭环

目标：系统自动运行、自动降级、自动恢复，管理员只处理真正需要判断的异常。

需要完成：

- 主 Feed、官方字段、历史复核、失败队列分别使用独立租约和运行记录。
- 过期租约自动释放，过期运行自动标记 stale，不能依赖人工清理。
- 失败队列按 1 分钟、5 分钟、30 分钟、2 小时退避；达到上限进入 dead。
- 同一官方 host 限制并发和请求间隔，不能因三家公司并发造成供应商封禁。
- 上游目录快照失败时保留上一次可信数量，并在大屏显示快照过期。
- 每天生成公司级健康报告，每周生成全公司对账报告，每月抽样验证官网、上游、数据库和公开 API。
- 所有人工操作返回操作 ID、实际影响记录数和后续状态，并写入管理员审计日志。

## 17. 岗位更新及时性和准确性验收指标

这些指标是 AI 选岗前置条件：

| 指标 | 目标 | 不达标动作 |
| --- | --- | --- |
| 上游到网站新增延迟 | 通常不超过 15 分钟 | 检查主 Feed 调度、上游接口和游标 |
| 官方关闭到网站下架延迟 | 完整快照确认后一个同步周期内 | 检查关闭事件、快照完整性和公司状态 |
| 主 Feed 游标无进展 | 超过 15 分钟报警 | 保留游标，定位页面级失败，不重置游标 |
| 行级失败 | 不阻塞同页，进入失败队列 | 检查标准化和数据库单条写入 |
| 页面级失败 | 不推进游标，不关闭岗位 | 重试当前页面并隔离公司 |
| 外部 ID 重复 | 0 | 立即暂停该公司写入 |
| 展示字段官方证据 | 100% 可回链 | 隐藏无证据值，不使用模型猜测 |
| AI 选岗岗位池新鲜度 | 只使用最近可信快照 | 过期公司标记不可作为“实时”依据 |
| 数据库/API/页面一致性 | 100% 抽样一致 | 暂停当前公司，不重建岗位 |

## 18. 最终执行原则

推进速度的关键不是同时打开更多公司，而是先让主 Feed 成为稳定、可证明的岗位生命周期通道，再利用独立队列快速补字段。任何时候都遵守以下顺序：

`主 Feed 新鲜度 → 官方快照完整性 → 岗位关闭准确性 → 字段证据质量 → AI 选岗可用性 → 大屏自动化和人工操作`。

如果主 Feed 没有最近成功记录、定时任务没有明确入口、运行记录存在大量 stale，优先修运行基础设施；不能用增加字段复核数量来掩盖岗位池没有及时更新的问题。
