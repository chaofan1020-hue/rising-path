# 公司岗位字段接入运行手册

更新时间：2026-08-28

这份手册是后续接入新公司的默认流程。公司之间允许有字段差异，但不再为每家公司重新发明一套同步、证据和验收方式。

## 一、先记住四层边界

每个字段都要沿着同一条链路检查，不能只看页面是否显示：

1. **官方源层**：公司官网、官方 ATS API 或官方详情页，记录 source URL、外部岗位 ID 和原始 payload。
2. **解析层**：把公司的原始字段解析为标准字段，保留原文和字段来源。解析失败只能让字段为空，不能让岗位被关闭。
3. **同步层**：标准字段写入 `jobs`，用“公司 + source_system + external_job_id”或稳定官方 URL 幂等匹配，不能因为字段补全改变 `is_active` / `is_closed`。
4. **展示层**：列表和详情页只展示有证据的字段；缺失就隐藏，不用标题、发布时间或模型猜测填充。

经验教训：只改前端不会修复数据库空字段；只改连接器也可能在上游标准化时丢失。每次字段问题都必须从原始 payload 一直追到页面。

## 二、单家公司标准流程

### 1. 登记和探测

- 先查已有公司、source、migration 和生产数据，避免重复建表或重复注册来源。
- 优先使用公开官方 JSON/API；其次使用官方 ATS（Greenhouse、Ashby、Lever 等）；最后才考虑官方详情页。
- 记录 board token、官方 careers URL、允许的官方域名、地区范围、时区和是否需要详情页。
- 不把密码、cookie、验证码绕过或服务器密钥写入代码、fixture 和文档。

### 2. 先做真实小样本

- 先抓取一页或不超过 20 条真实岗位，再做全量。
- 同时保存原始字段、解析结果和标准化结果，至少检查：标题、外部 ID、URL、地点、岗位类型、经验、薪资、截止日期、正文。
- fixture 只能证明规则没有回归，不能替代真实样本。真实样本必须覆盖普通岗位、实习/校招、多地点、远程、无经验和字段缺失情况。
- 解析失败数量、地区过滤数量和官网链接数量必须分别统计，不能只看最终写入数量。

### 3. 字段解析规则

- 复用 `src/lib/job-content.ts` 的 HTML 实体解码和富文本清理。Greenhouse 等源可能返回 `&lt;li&gt;`，甚至双重编码。
- 经验统一输出：`experience_min_years`、`experience_max_years`、`experience_text`。
- 经验规则覆盖 `5+ years`、`2-4 years`、`6mos-1 year`、`years' experience`、英文数字词和中文年限；只识别明确的工作经验。
- “18-24 months 后可以内部申请”“产品有 3 年历史”“公司有超过 30 年投资经验”“experience with Python”等不是候选人的经验要求，必须排除。
- 薪资必须同时有币种和金额；截止日期必须有官方字段或官网正文中的明确标签；没有证据就为空。官方 ATS 的结构化 `application_deadline` / `valid_through` 只有在 `source_type=official_ats`、字段来源为 `official_payload`、日期通过合理性校验且证据 URL 为该岗位官方链接时才可展示；普通 `collector_feed` 时间戳、隐藏元数据和历史日期即使格式合法也必须隐藏。
- 地点先保留官方原值，再做去重、远程识别和目标地区过滤；不能因为一个未知地点让整家公司或整次同步失败。
- 公司特有字段放在公司/连接器映射中，通用清洗、证据格式和生命周期规则不要复制多份。
- 某些 ATS 的列表会短暂保留已关闭岗位。但不能仅用 HTML 中出现的 `filled`、`closed` 或 `no longer available` 判定关闭：Phenom 等页面可能在有效岗位详情旁预置隐藏的过期组件。必须先验证详情是否存在与 URL 外部 ID 一致的官方岗位数据；只有缺少匹配详情数据且明确显示关闭页时，才排除字段回填并单独统计。此判定本身不改变既有岗位生命周期，仍由独立的链接健康流程按官网证据处理。
- 链接健康服务为了安全限制会截断大页面。对于 Phenom，若完整 `jobSeqNo` 位于截断边界之后，但前段仍包含官方 `phApp.ddo.jobDetail.data.job` 数据包，必须把它当作有效详情而非关闭页面；否则用户打开岗位详情可能错误触发下架。回归测试必须覆盖“完整 JSON 截断但官方详情包仍可识别”的情形。
- 对已登记的 Phenom 公司，通用 HTML 链接检查不能单凭 `filled` 文案关闭岗位，因为该模板会固定渲染过期组件且纯文本安全抓取会移除脚本数据。其生命周期仍由官方连接器的列表/详情探测和上游关闭事件决定。该豁免必须同时校验公司、官方 host 与 `/job/{id}` 路径；不能推广到未登记公司或其他 ATS。

### 4. 写入前预览

先运行 dry-run，确认收到、解析、标准化、过滤和候选写入数量：

```bash
pnpm run sync:job-connector -- --company=Cloudflare
```

预览至少要回答：

- 官方收到多少条，解析丢了多少条，为什么丢。
- 地区过滤掉多少条，是否符合公司的地区范围。
- 每个标准字段的覆盖率和来源是什么。
- 现有岗位按外部 ID/URL 能匹配多少条，是否会产生重复。
- 是否有字段异常，但岗位本身仍应保持开放。

### 5. 回填和正式写入

- 首次接入通过样本验收后才允许写入；写入必须有显式环境开关。
- 已有岗位字段修复使用“只补缺失字段”的回填脚本，按官方外部 ID 匹配，并加 `is_active=true` 条件。
- 回填前先预览，回填后再查覆盖率、官方证据数量和岗位生命周期数量。
- 不用全量删除重建，不改变收藏、投递、AI 匹配所依赖的岗位 ID，不因字段缺失关闭岗位。

#### 生产环境回填防呆（Cloudflare 事故复盘）

2026-08-28 的 Cloudflare 经验回填曾出现“脚本显示回填完成，但网站大部分岗位仍没有经验要求”。根因是回填脚本默认读取本地 `.env.local`，该文件指向测试 Supabase；测试库的成功统计不能证明生产库已更新。

后续所有会写入岗位数据的脚本必须遵守以下顺序：

1. **先确认环境**：在输出和运行记录中明确标记目标为开发、测试或生产，并核对 Supabase project ref、目标公司和 `is_active` 岗位数；不得把密钥写入输出、日志或文档。
2. **生产环境显式注入**：本地执行生产回填时，显式使用生产环境配置；在生产服务器执行时，使用 `/opt/liorvix/.env.local`。不能依赖工作区根目录 `.env.local` 的默认值。
3. **先 dry-run**：确认官方接收数、解析数、现有岗位数、外部 ID 匹配数和候选更新数都来自目标生产库，才允许添加 `--write`。
4. **写入后双重核验**：先直接查目标生产库的字段覆盖率和 `field_evidence`，再请求公网 `/api/jobs` 与至少一个 `/api/jobs/{id}`。数据库、API 和页面三者都一致才算完成。
5. **记录环境与时间**：覆盖率统计必须附带环境和查询时间。招聘源会变化，不能把测试环境、旧时间点或别的 Supabase 项目的数量当作生产验收结果。

本次生产库修正后，Cloudflare 在招岗位中有 163 条带有官方 Greenhouse 经验要求和字段证据；其余岗位只有在官网存在明确经验要求时才会填充，保持为空是正确结果，不应用猜测补满。

## 三、测试和部署门槛

每家公司至少添加 20 条 fixture，并覆盖无经验、技能描述、范围、月/年混合、HTML 实体编码和字段缺失。至少运行：

```bash
pnpm test:job-connectors
pnpm test:job-standard-fields
pnpm test:job-maintenance-content
pnpm test:job-content
pnpm ts-check
```

然后才构建和部署。生产发布前确认：

- 数据库迁移已是最新，不为字段修复重复执行历史迁移。
- 构建会检查 `scripts/` 下的 TypeScript 文件，新增审计脚本也必须通过 `pnpm ts-check`。
- 发布后检查 `systemctl is-active liorvix`、本机 `/api/health` 和公网 `/api/health`。
- 检查服务日志中同步的 `received / parsed / normalized / filtered / failed` 数量，确认没有异常骤降。
- 对任何数据回填，额外记录目标 Supabase 环境、dry-run 结果、写入结果、生产库覆盖率和公网 API 抽样结果；只看到脚本的“成功”输出不能算验收通过。

## 四、遇到问题时的固定排查顺序

1. 从官网/API取一条真实原始岗位。
2. 打印原始字段、HTML 清理结果、解析结果和 `normalizeFeedItem` 结果。
3. 检查是否在地区过滤、证据策略、同步保留逻辑或数据库展示层丢失。
4. 加最小真实回归 fixture，再改通用解析器。
5. 先 dry-run，再做只补字段的回填，最后部署。

不要先迁移数据库、不要先改页面文案、不要直接全量重建，也不要用模型推断没有官方证据的字段。

## 五、可复制的接入清单

- [ ] 已确认唯一官方源、board token、官方域名和地区范围。
- [ ] 已抓取至少 20 条真实样本并保存脱敏 fixture。
- [ ] 已验证外部 ID、URL、地点、岗位类型、经验、薪资、截止日期和正文。
- [ ] 已确认解析层和上游标准化层使用同一套通用规则。
- [ ] 已确认字段证据包含来源 URL、字段来源和核验时间。
- [ ] 已确认字段异常不会改变岗位上下架状态。
- [ ] 已完成 dry-run，解析丢失和地区过滤均有解释。
- [ ] 已完成连接器、标准字段、内容和 TypeScript 测试。
- [ ] 已完成只补缺失字段的回填预览和结果核对。
- [ ] 已确认回填脚本实际连接目标 Supabase 环境，dry-run 和 `--write` 的 project ref 一致。
- [ ] 已从生产数据库、公网 API 和实际页面三处抽样确认字段都已显示。
- [ ] 已部署并检查服务、健康接口、同步日志和公网页面。
- [ ] 连续 3 个同步周期稳定后，才标记为常规来源。
