# 岗位字段第一阶段执行计划

更新时间：2026-09-02  
适用环境：生产 Supabase `weqvdtdjdzmqflhwobec`  相关服务器：`43.172.117.125:/opt/liorvix`

## 一、阶段目标

第一阶段只做一次完整、可追溯的现状盘点，回答五个问题：

1. 当前有哪些公司、在招岗位和官方来源。
2. 哪些公司已经完成字段回填，哪些只是来源被识别，哪些还没有完成官方源探测。
3. 六项标准字段分别缺多少，缺失是官网未提供、暂时待复核、历史数据被隔离，还是尚未接入解析流程。
4. 哪些岗位字段任务、连接器任务、内容质量任务和同步任务仍未完成。
5. 后续应该先处理什么，哪些任务可以自动化，哪些任务必须先完成官方证据确认。

第一阶段的交付结果不是“把字段补满”，而是把所有未完成事项变成有负责人边界、有证据、有下一步动作的清单。

## 二、范围和禁止事项

### 本阶段包含

- 读取交接文档、运行手册、执行日志、代码和迁移记录。
- 只读核对生产环境、Supabase project ref、服务状态、同步队列和失败队列。
- 生成生产公司来源矩阵和六项字段覆盖率。
- 盘点描述、任职要求、官方 URL、外部 ID、学生相关字段和岗位生命周期的现状。
- 对已完成、进行中、待探测、待复核和未知任务进行分组。
- 形成下一阶段的优先级、进入条件和验收标准。

### 本阶段禁止

- 不执行任何 `--write`、生产字段回填或来源台账写入。
- 不开启 `JOBS_CONNECTOR_BACKFILL_WRITE_ENABLED` 或其他生产写入开关。
- 不修改 `jobs` 的字段、`is_active`、`is_closed`、岗位 ID、收藏、投递记录或 AI 匹配记录。
- 不强制释放有效租约，不重置游标，不重建岗位。
- 不因为字段为空、详情失败或解析异常关闭岗位。
- 不把“没有证据”写成“官网没有提供”；不使用模型猜测经验、薪资、截止日期或学生资格。

## 三、执行顺序

### 阶段 1：环境和资料确认

**目的：** 防止把测试库、旧报告或错误服务器状态当成生产事实。

**工作：**

- 阅读 `job-company-field-connector-runbook.md` 和 `job-company-onboarding-runbook.md`。
- 阅读岗位字段交接单、完成总结、执行日志和全公司计划。
- 通过 SSH 只读确认服务器目录和 Supabase project ref。
- 确认生产服务、Node 进程、环境变量和旧 systemd timer 状态。
- 记录本次盘点时间、数据环境和命令入口。

**产出：**

- 环境核验记录。
- 本次盘点的 UTC 时间和北京时间。
- 生产 project ref 必须为 `weqvdtdjdzmqflhwobec`。

**通过条件：** 环境不一致时立即停止后续生产检查，不执行任何写入。

### 阶段 2：公司和官方来源盘点

**目的：** 建立当前活跃公司的唯一总表，避免将公司名称、来源族和连接器状态混为一谈。

**工作：**

- 从生产 `collector_feed` 岗位聚合公司、在招数量、官方 URL host 和外部 ID 情况。
- 读取上游公司目录，核对公司是否有上游 ID。
- 对每家公司标记来源族：Greenhouse、Ashby、Lever、Phenom、Workday、Oracle HCM、Apple API 或自建/未分类。
- 对每家公司标记来源状态：
  - `completed_baseline`：已有完成验收基线。
  - `queue_in_progress`：已有队列但仍在推进。
  - `source_identified_pending`：来源族已识别但没有完成公司级验收。
  - `discovery_required`：还没有可验收的官方连接器或官方源结论。
- 特别检查来源矩阵和 `job_sync_state` 中是否存在孤儿公司、旧来源或重复来源。

**产出：**

- `phase1-source-matrix-production-<date>.json`。
- 公司、岗位数、来源族、来源 host、上游 ID、连接器状态和队列状态表。
- 来源状态异常清单。

**通过条件：** 所有活跃上游公司都有记录；未知来源明确标记为 `discovery_required`，不被强行归类。

### 阶段 3：六项标准字段覆盖盘点

**目的：** 把“字段没有值”拆成可处理的原因，而不是用一个总缺口数字误导后续回填。

**字段范围：**

- 地点 `location`
- 工作方式 `workplace_type`
- 岗位类型 `employment_category`
- 经验 `experience`
- 薪资 `salary`
- 截止日期 `deadline`

**每个字段必须统计：**

- `verified`：有可验证官方证据且当前有可展示值。
- `pending_recheck`：存在值或待复核证据，但需要重新检查官方源、解析或详情。
- `rejected_legacy`：历史值已隔离，不能展示或不能继续作为证据。
- `unavailable_on_official_source`：当前没有形成可用证据；只有在官方源已确认并检查过后，才可以解释为官网未提供。

**工作：**

- 从生产字段覆盖审计获取全站和公司级数字。
- 检查 `field_evidence`、字段来源、证据 URL 和验证时间是否一致。
- 找出“有值但没有 verified 证据”和“有 verified 证据但当前无值”的记录。
- 对字段缺口按公司、来源族和岗位类型排序。

**产出：**

- 全站字段覆盖表。
- 公司级字段覆盖表。
- 待复核原因分类表。
- 历史证据残留清单。

**通过条件：** 不能把官网未提供、详情暂时失败、历史脏数据和解析缺陷合并成一个“缺失”类别。

### 阶段 4：内容、学生字段和生命周期盘点

**目的：** 确认系统是否已经具备服务学生用户所需的岗位判断信息。

**工作：**

- 抽样检查标题、正文、任职要求、官方 URL、外部 ID 和当前岗位状态。
- 分别统计正文缺失、正文过短、详情不可访问、只有 ID 占位正文和正常正文。
- 检查上游是否提供 `education_level`、`level`、`employment_type`、`experience`、`valid_through`、`remote_type`、`work_arrangement`、`workplace_type`、`recruiting_program` 等字段。
- 检查当前 `job_type` / `employment_category` 是否仅依赖标题、`employment_type` 和 `level`。
- 记录学生信号，但本阶段不写入新字段：
  - Internship / Intern
  - Co-op
  - New Grad
  - Campus
  - Early Career
  - Entry Level
  - Graduate Program
  - Analyst Program
  - Student
- 单独核对 `status`、`sync_action`、`valid_through` 的关系，防止把截止日期过期误当作岗位关闭。

**产出：**

- 内容质量抽样报告。
- 学生字段可用性报告。
- 学生岗位分类缺口表。
- 生命周期风险清单。

**通过条件：** 能明确哪些学生信号来自官方结构化字段、官方正文、标题或尚未有证据；标题推导不能冒充官方字段证据。

### 阶段 5：同步队列和生产服务盘点

**目的：** 确认岗位是否能及时进入系统，以及新增岗位字段是否真的会自动处理。

**工作：**

- 检查主 `collector_feed` 游标、最近成功时间、失败次数、租约和失败队列。
- 检查每家公司 `official:*` 游标、末端岗位 ID、冷却时间和最后成功时间。
- 检查 `JOBS_SYNC_INTERVAL_MINUTES`、详情批量大小、公司数、请求间隔和并发配置。
- 核对 `JOBS_CONNECTOR_BACKFILL_WRITE_ENABLED` 是否开启；未确认前不能宣称注册连接器公司会自动写入新增字段。
- 检查 Web 服务和后台 worker 是否共用 Node 进程。
- 检查服务重启次数、旧 timer 是否重复调度、服务是否以 root 运行。

**产出：**

- 主同步健康快照。
- 官方详情队列快照。
- 自动写入能力确认结果。
- 服务进程和调度风险清单。

**通过条件：** 队列没有失败或卡住租约；即使队列正常，也要单独记录周期过长、完成冷却和写入开关等性能/功能风险。

### 阶段 6：未完成任务登记和优先级排序

**目的：** 把盘点结果转成后续可以逐项关闭的任务，不再依赖聊天记录判断“做到哪了”。

**任务分类：**

| 优先级 | 任务类型 | 例子 |
| --- | --- | --- |
| P0 | 环境、证据和安全防错 | project ref、生产写入边界、孤儿状态、数据口径 |
| P1 | 学生用户直接相关 | 实习/校招/新毕业生信号、经验筛选、截止日期优先级 |
| P1 | 新岗位新鲜度 | 增量周期、游标延迟、临近截止岗位处理 |
| P1 | 现有字段补齐 | 已确认来源公司的待复核和只补缺失字段回填 |
| P2 | 新来源接入 | Oracle HCM、Apple API、自建站点和未分类来源探测 |
| P2 | 服务性能 | Web/worker 拆分、API 查询、分页、缓存、索引 |
| P3 | 历史低价值清理 | 无官方证据的历史字段、低优先级内容复核 |

每条任务必须包含：任务编号、公司或来源族、岗位数量、当前状态、证据位置、风险、下一步、是否允许写入、完成标准和最后核验时间。

**产出：**

- `job-field-task-inventory-20260902.md` 更新版。
- 未完成任务清单。
- 后续处理顺序和进入条件。

### 阶段 7：阶段验收和交接

**目的：** 确认盘点完整且没有把只读检查误当成数据处理。

**验收清单：**

- [ ] 生产 project ref 正确。
- [ ] 活跃公司数量、在招岗位总量和上游目录已记录。
- [ ] 每家公司都有来源族和来源状态。
- [ ] 六项标准字段都有全站和公司级覆盖率。
- [ ] `verified`、`pending_recheck`、`rejected_legacy` 和未形成证据已分开。
- [ ] 学生相关上游字段和当前分类规则已盘点。
- [ ] 主同步、官方详情队列、失败队列和租约已核对。
- [ ] 新增岗位自动字段写入能力已明确为“已确认、未确认或未开启”。
- [ ] 所有未完成工作都有下一步和完成标准。
- [ ] 本阶段没有执行生产写入或改变岗位生命周期。

## 五、第二阶段进入条件

只有满足以下条件，才进入字段补齐或学生分类的代码/生产实施：

- 第一阶段总表已确认没有未登记的活跃公司。
- 每个待处理公司都有官方来源、官方 host、稳定外部 ID 和地区范围结论，或明确记录为无法确认。
- 每个待补字段都有来源证据策略和字段映射。
- 学生岗位分类的标准字段、信号优先级和证据等级已经确定。
- 已登记连接器公司的生产写入开关、队列行为和游标推进方式已经确认。
- 每家公司都有 20 条真实样本的 dry-run 方案。
- 后续写入计划明确只补缺失/未验证字段，不改变岗位生命周期。

## 六、计划完成定义

第一阶段完成不等于六项字段全部有值，而是：

- 公司全集完整。
- 来源状态清楚。
- 字段缺口可解释。
- 学生用户相关数据缺口已显式登记。
- 同步和服务瓶颈有证据。
- 未完成工作可排序、可复跑、可验收。
- 所有生产写入都留到后续阶段，并继续遵守公司字段接入运行手册。
